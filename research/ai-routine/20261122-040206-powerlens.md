# PowerLens card refinement

Date: 2026-11-22 04:02 KST

## Candidate decision

- Existing AI+Android research card; refined as an architecture/security case study, not as a deployable product recommendation.
- Adjacent MNN-AECS card is related only at the broad energy-efficiency level. MNN-AECS optimizes LLM decode-time CPU-core selection inside an inference engine; PowerLens changes OS/system settings through a context-aware agent. Their mechanism, prerequisites, and learning objectives differ, so they remain separate one-minute cards rather than a combined overloaded card.
- Popularity/adoption signal is weak: GitHub repository search for `PowerLens Android LLM` returned zero repositories. The author project page states “Under Submission” / “Under Double-Blind Review.” No public implementation was verified. This is retained as a research-method and agent-safety lesson, not labeled hot, broadly adopted, or production-ready.

## Sources checked

- arXiv abstract: https://arxiv.org/abs/2603.19584

## Fact-check

- Paper abstract and full text describe a multi-agent Android power-management prototype using UI hierarchy/device state, 18 system parameters, a PDL constraint checker, and implicit user feedback.
- Implementation section states the app targets Android 7.0+ (API 24) but requires root (`su`) for system-level parameter control. It describes four sequential Gemini-2.5-Flash API calls per decision cycle.
- The PDF's execution section describes an LLM call for shell-command generation and subsequent state read-back. However, the author project page describes command compilation as deterministic table lookup, with no LLM at execution. This is a material discrepancy in a safety-critical privilege boundary. No public source repository was found to resolve it; the card explicitly reports the inconsistency rather than choosing one account.
- The headline benchmark numbers (38.8% energy saving, 81.7% action accuracy, 0.6% violation rate) are author-reported results for a rooted OnePlus ACE 5 (Snapdragon 8 Gen 3, 12 GB RAM) running Android 15 with KernelSU. They are not general Android app results. A separate 14-day study used 10 participants and 8 rooted devices; it does not establish support on ordinary unrooted consumer devices.
- The 0.5% daily battery-overhead claim was removed from the card because the paper extrapolates a typical day from a 30-minute dry-run and approximately 80 decision cycles; it is not a broad per-device measurement.
- The design lesson remains valuable: separate policy generation from deterministic authorization/execution; audit root scope, outbound model/data flows, hard constraints, command validation, state read-back, and rollback.

## Duplicate and confidence

- No duplicate card found for the combination of root access, cloud LLM power-policy generation, and a conflicting execution-path description.
- Distinct from MNN-AECS: system/OS policy versus inference-runtime scheduling.
- Confidence: high for what the paper and project page state; low for implementation reproducibility and general applicability because no code is public and the two sources disagree.
