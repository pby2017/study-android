# A2A: Agent Card discovery and Task lifecycle

Reviewed: 2026-11-22 (KST)

## Card decision

Replaced the anniversary-led description with the durable protocol concepts: Agent Card discovery, Task lifecycle, and the protocol boundary with MCP. The card's interview answer focuses on an easy-to-miss trust boundary: metadata describing authentication requirements does not authenticate a caller or authorize an action.

## Evidence checked

- A2A current specification: https://a2a-protocol.org/latest/specification/
- A2A Agent Card and discovery: https://a2a-protocol.org/latest/specification/agent-card/
- A2A 1.0 announcement and backward-compatible migration context: https://a2a-protocol.org/v1.0.1/announcing-1.0/
- MCP specification (2025-11-25): https://modelcontextprotocol.io/specification/2025-11-25

The A2A spec describes the Agent Card as a self-describing manifest with identity, capabilities, supported interfaces, and security requirements. Task APIs track status and artifacts, and streaming can return progress/status and artifact updates. MCP defines host/client/server roles and resources, prompts, and tools for LLM applications. Its security section requires implementers to address consent and authorization; it explicitly notes the protocol cannot enforce all security principles itself.

## Editorial choices and caveats

- Removed the stale one-year framing and the unsupported claim that splitting agents inherently reduces context pollution or privilege expansion.
- Removed the speculative Android AppFunctions-to-A2A architecture suggestion; it was not needed to teach the protocol boundary.
- Do not infer that a published Agent Card is trustworthy, that its advertised authentication is sufficient, or that the protocol guarantees task authorization.
- Do not present MCP and A2A as competitors: their core interaction boundaries differ and a system may use both.
